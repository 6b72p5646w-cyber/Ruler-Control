# BC02：正常顾客公共路线与原物前置链

## 1. 已补齐什么，仍未声称什么

BC02 现在把 12 个可奖励设施来源全部接到了可执行的正常顾客路线：顾客沿真实 StoreMap 的身体可通行路径移动，完成有实际时长的动作，原库存/原包裹/原饮品发生可追溯状态变化，最后生成同一已付订单的使用回执并交给 `FacilitiesBC02.customer_use`。监控 FR07 与照明 FR08 继续承担员工控制、信息与真实光照职责，没有为凑覆盖而制造顾客奖励。

权威规格是 `content/customer_routes_bc02.json`；执行参考是 `scripts/bc02_customer_reference.py`；检查脚本与机器证据分别是 `scripts/check_bc02_customer_routes.py`、`docs/bc02_customer_report.json`。这是 **公共路线、物件与履约链的参考实现**。完整随机到访/入侵导演、真实客户端 NPC、真实库存后端和持久化事务尚未接线；`actual_client_runtime=false`，不能把参考模型结果称为客户端已完成。

## 2. FR06 原来能走到，但并不等于能给顾客使用

旧地图的 `verification_desk=[25.5,27.5]` 位于核验台 FX23 的南面，是原员工身份核验操作位。BC01 的公共路径策略曾把它列为顾客可用，旧路径算法也能从入口走到那里，距离 20 格。这只证明没有实体墙挡住，不能证明员工操作面可以给普通顾客用。

BC02 新增独立公共面，并明确保留原员工控制：

| 用途 | 名称与位置 | 实体/权限 |
|---|---|---|
| 顾客取件核验 | `bc02_customer_verification=[25.5,24.5]` | FX23 `[25,25,4,2]` 的北侧公共读码面；0.3 格身体半径可达 |
| 原员工核验 | `verification_desk=[25.5,27.5]` | 原员工南侧控制保留，普通顾客路径禁止进入其操作侧 |
| 顾客就地饮用 | `bc02_customer_drink_spot=[7.5,23.5]` | 收银公共侧旁的合法地格，不是 FR13 公共供给台 |
| 公共供给台 | `public_supplies=[22.5,21.5]` | 已有公共柜西侧，承担 FR13 |

`CustomerStoreMapBC02` 继承现有 StoreMap 的真实实体、门、身体半径和四邻接地格，增加新公共 anchor；顾客图额外排除收银员工侧 `[2,26,7,2]` 及核验员工侧 `[25,27,4,2]`，玩家仍可以走原员工路径。FR06 的设施合同也已改为新公共名字，不用别名假装旧坐标正确。

所有新公共面与客户路径都进入临时陷阱的保护格。基础地图在这些保护加入后仍有 10 个合法 1×1 摆放候选、16 个含旋转的 1×2 摆放候选；不是以堵死陷阱系统换取公共路线。动态障碍会减少候选，落地时仍须按实际容量与几何重新验证。关门时没有合法顾客路径就拒绝该到访；已经行走时几何版本变化会停止旧路径并要求重规划，不穿过新关上的门。

## 3. 班前偏好选择与每单两个服务

玩家在 PREP 选择可接受的服务 profile，营业开始后冻结该选择。真正的到访导演应从偏好、实际库存、合法路线和当前供电中挑选顾客需求；选择 profile 只选择路线倾向，不直接增加支援份数。低客流可以只发生几单，不保证把 14 个设备全部覆盖。

一单的可选奖励服务最多两个。实际结账 FR01 与实际完成交付后的离店 FR10 为自然事件，独立计数。一个商品领取本身就占一个可选服务名额，不能再附两个奖励服务。这里给出四类普通商品的基础路线、各自的小票服务路线，以及四类专门链：

| `goods_basic` | FR02 | 原货架商品领取→付款→离店 | 62 格 / 3 秒 / 28.833 秒 |
| `goods_lucky` | FR02、FR14 | 原货架商品→付款→扫同张小票→离店 | 86 格 / 4.5 秒 / 40.333 秒 |

| `frozen_lucky` | FR04、FR14 | 普通冻货→付款→扫同张小票→离店 | 106 格 / 4.5 秒 / 48.667 秒 |

上述时间为基础动作时长、顾客速度 2.4 格/秒、无其它客户排队和无遮挡基础地图的 **实际路径参考结果**，由 `路径长度 / 2.4 + 实际动作时长` 复算，不是距离直线估计，也不是上线排队表现承诺。准备与玩家战斗之间的完整调度仍由导演承担，不能因一条 profile 理论上 40 秒就承诺任意时点都能安全做完。

### 3.1 FR05 + FR11：喝完是前置动作，不是第三个设施奖励

顾客先取得、支付本单冷饮，走到收银旁就地饮用位，用 2 个实际世界秒喝完原饮品。饮用动作本身不登记 FR13。原饮品变为 `consumed`，其原容器以固定 `原 item_id:empty:1` 派生为空杯记录，保留同一个 `material_unit_id`、原父物件、客户、订单 root 与实际饮用回执。

空杯之后被带到公共回收面，用 1.5 秒完成 FR11。回收要求同一原饮品、同一个物理容器、同一已付订单、确实完成过 2 秒饮用，以及当前仍由该顾客持有；不能拿一只任意杯子来顶替。回收后变成不可售废弃物，退款和回补可售库存都为 0。原饮料和空杯不会同时是两件可用物品，玩家也得不到一个免费饮料。

因此本单奖励来源只有 FR05 + FR11。FR05 + FR13 是另一条独立路线：去公共供给面完成相同原饮品的真实饮用，发 FR13，顾客带空容器离开；没有再发 FR11。不能在同单上拼出 FR05 + FR13 + FR11 三份奖励。

### 3.2 FR06 + FR12：包裹是原雇主货，不再挤入第三次货架服务

班前只能用一件确实存在、未预留的 employer 商品和一只确实存在、未使用的 employer 包装袋执行预包装事务。商品进入这只原袋，原袋成为 `sealed_parcel`，保留商品、袋子两份原输入 ID 和打包回执；没有生成第二份商品。已经打包的商品/袋子不能再打一次，也不能同时留在可售货架池。

该顾客订单只销售这一件原密封包裹；支付时将袋和内部原货一起转给该客户。公共核验读取其原订单和原包裹编码，1.5 秒完成后留下实际核验回执；自提要求这个回执与客户、订单、bag ID 完全相符，再用 1.5 秒领取同一个原包裹。它的两个可选奖励服务为 FR06 和 FR12，不额外模拟一次 FR02 货架购买。没有第二次收钱、第二份商品或第三个服务名额。

### 3.3 FR03 + FR09 与 FR14

叫号热食路线先从真实热食库存预留一份原物。顾客支付后，广播实际发出自己的原订单号，顾客在真实等待位置花 1 秒回应；之后沿路径去热食点拿走被锁给自己的那一份。叫号记录必须有原顾客、原订单、原付款回执、实际源位置与听者位置；并在通电状态下完成回应。断电不能用一张纸号伪造广播使用。

小票路线可接任一种普通商品，但只扫描同一张原已付小票一次。它不新造订单、不把物品发给玩家、不动玩家抽奖券与保底，也不调用广告额外抽奖。FR14 的三选一支援仍由 FacilitiesBC02 在第一次有效使用时固定。

## 4. 付款、交付与离店必须分开

### 4.1 已付款不等于已经履约

`hot_called` 与 `parcel_verified` 都可能在付款以后、取件以前遇到 OMEN。此时不能让客户消失、原物消失，或直接把 FR03/FR12/FR10 当作已经完成。

选择的方案是保留免费领取权，安全撤离优先：

1. `evacuate_paid_uncollected` 暂停普通服务计划，将同一原 item/order/customer/logical IDs 与原付款快照形成唯一 `pickup_entitlement`。物品仍锁在实际原热食槽或原自提槽，没有瞬移到另一个仓库。
2. 顾客沿当前真实公共路径走到离店边界。此段 OMEN 只执行物理撤离，不继续核验、叫号、取件或其它杂活。
3. 已真实完成的收银 FR01 可以保留一次；未做的取件/热食领取不发对应支援，未交付的这次撤离不发 FR10。未履约不是完整顾客服务。
4. 领取权进入持久检查点，包含原物和嵌套内容、原付款、已有打包/核验回执、已完成设备操作与同单去重身份。它是店铺履约记录，不能被算成一个永不结束的怪物威胁；在记录可靠保存后可正常结束本夜。

### 4.2 同夜返回：免费补原物，只补原单未完成的使用

当真实导演重新进入安全 BUSINESS，`resume_pickup` 让原顾客从实际入口再来，沿原物所需的剩余叫号、核验和领取路径完成交付，再真实离店。已经完成的同单核验或叫号不重复领取支援；取件与离店才补发它们尚未处理的同单使用回执。

没有第二个 `order_paid`，没有再次扣钱或再发订单金币/XP，使用原订单和原客户身份去重。原有 FR01 不重发；原 FR10 先前没发过，完成实际交付和离店后才发一次。若入侵再次打断，仍围绕同一原货与领取权保存，不在 RAID 催玩家补办。再次撤离合并原领取权，不能覆盖掉持久 `resume_count`；访问编号递增为 `visit:2`、`visit:3`，导出/导入后也保留。访问实例彼此独立，原订单/设施发奖 ID 仍保持同一份去重身份。

### 4.3 跨夜返回：原承诺免费履约，前夜储备不带入新夜

跨夜导出/导入领取权时保留原商品、原付款夜、原尝试、原客户和逻辑订单身份。原客户下一夜仍可免费领走自己的原物。该次旧单履约 **不生成新订单金币/XP、不补发新夜设施储备，也不发 FR10 存活额度**。

不能把旧付款回执的 `night_id` 改成新夜来绕过设施强校验。参考实现直接对旧夜/旧尝试的完成履约返回零当夜 `customer_use` 请求；当夜新订单继续按当夜真实来源正常结算。领取完成后关闭该领取权，不能反复用它领取商品或收益。

目前参考中实际检查了包裹、热食各一次同夜续领与跨夜领取，总共四个保存/撤离/继续案例。完整导演触发 OMEN 的挂接、生产持久化的原子提交、未支付和已完整拿到商品的其它撤离分支仍是后续客户端任务，不能用这四个范围案例替代全部 NPC 调度。

## 5. 回执如何证明不是硬填布尔值

路线参考先产生自己的行动和物件账本，`build_use_requests` 只接受与本模块保存的真实完成 journey 完全一致的记录。外部把 action 的时长改成 0、伪造一个完成列表，都会被拒绝。

设施消费所需字段由以下实际记录计算：

| 设施输入 | 真正来源 |
|---|---|
| `normal_customer` / `customer_kind` | 本路线工厂创建并登记的正常顾客实例 |
| `actual_use_completed` / `progress_complete` / `use_duration_s` | 实际动作推进完毕的回执、耗时、位置和完成世界时间 |
| `facility_geometry_bound` | 新旧明确公共 anchor、实际身体可通行点、当前导航版本、实际动作位置相等 |
| `source_item_owner_customer` | 付款后的原物 owner，或 FR11 同一回收记录里真正转交前的 owner |
| `same_order_service` / `source_root_id` | 预留原物、顾客、逻辑订单 root 与履约记录一致 |
| `route_service_authorized` | 班前选定的该 profile 的最多两个服务，及独立的结账/离店自然事件 |
| `paid_order_receipt` | 实际支付动作生成的固定付款字段，加只追加的真实履约日志 |
| `exit_boundary_crossed` | 顾客沿长度大于 0 的真实公共路线到离店点，且原物已交付；未领货安全撤离没有 FR10 操作 |

付款时间、原客户、原订单、原商品和金额在支付后不可改写。`facilities_used` 是原付款对应的只追加履约日志，允许记录付款之后才发生的叫号/热食领取/包裹核验/扫码；这些新事实没有倒填为付款瞬间已经发生。最终回执中的商品身份仍是原支付承诺的同一件物品。

设施模块同步实际电源事件和世界时间后，使用现成 `FacilitiesBC02.customer_use` 的原身份/付款/历史用电/原物校验；不在测试里额外补 `facts=True`。普通手工结账在断电时仍能完成真实付款和商品离店，但没有电器 FR01 支援；前 0.75 秒断电、后 0.75 秒通电的 1.5 秒付款也不发 FR01。收银的手工付款进度不会因为电力变化被重置。广播等必须通电的服务被中断则不算完成，来电后需要重新完成本次真实动作。

为避免“同一时刻先完成、随后停电”被倒判为停电中操作，实际动作开始、完成与电源变化共用带 `source_event_stream_id`、递增 `sequence` 的事件流。实际完成回执保存完整 `started_event` 和开始/完成电源 epoch；设施 consumer 将这些记录与同订单/同顾客的动作回执及自己收到的电源历史逐项核对。同刻完成序号小于随后断电序号时，已完成使用有效；不能用一个 `source_powered=True` 布尔值代替证据。服务区间 `[19,22]` 即便两端都安全，只要穿过实际 RAID `[20,21)` 也必须拒绝。

## 6. 可执行检查与 Codex 接口

运行：

```bash
python scripts/check_bc02_customer_routes.py
python scripts/check_bc02_facilities.py
```

路线检查覆盖全部 12 个可奖励来源，包含公共权限、实际逐段移动、路径距离/时间复算、12 个正向 profile、缺空杯、未支付、跳过饮用、错误原物、跨订单 root、原库存不在实际槽位、断电中断、手工断电结账、两服务上限、库存耗尽、包裹输入/核验、关门、运行中几何改变、暂停、快照、一次性发布，以及已付未领的同夜/跨夜领取权、同刻完成后断电、半手工半通电收银、同一领取权两次中断后继续与跨夜后再次中断。生产状态在报告中仍明确为 `false`。

Codex 后续接线需使用以下边界：

- PREP：接入实际 employer 库存和预包装事务，收集服务偏好；每夜只加载一次真实来源，不能每到一个顾客都重造库存。
- BUSINESS：由真实导演调度已选且条件成立的 profile；把顾客移动和操作绑定实际 NPC，收银步骤还须绑定在原员工控制面的真实玩家交互。
- OMEN：预警回调中先停止普通服务；对已付未领热食/包裹执行本规范的原货锁定、真实撤离及持久领取权。不要把领取权登记成必须在战斗中完成的杂活。
- 结算：原付款事件由唯一经济账本消费一次；未交付领取权在原子存档中保存后才允许关闭夜局。前夜领取权不能给新夜刷订单或储备。
- 设施：仅消费来源账本生成的回执；保存 `published_use_ids` 与同单 ledger，保证部分履约、重新到访和重发不会再次发奖励。
- 暂停与广告：冻结统一世界时间及动作进度；广告奖励不能补全顾客路径、制造容器、补原物库存或扫描顾客小票。

这些接口仍需要客户端真正接线和实际玩法验收。路由参考提供了能检查的前置链，完整随机导演不能通过直接调用 `resume_safe_business` 来绕过怪物清场；生产实现须由它自身的真实安全阶段事件授权这一转移。
